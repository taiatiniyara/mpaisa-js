Why mpaisa-js

Built for the safe path. Every default pushes you toward the secure integration.

🔐

Tamper-proof redirects

tokenv2 hashes are recomputed locally with timing-safe comparison. Verification failures throw — you can't accidentally ignore them.

🧾

Two-step confirmation

confirmRedirect() verifies the hash first, then fetches authoritative status from the gateway. Never fulfil an order from the redirect alone.

🪶

Zero dependencies

Pure fetch + WebCrypto. No polyfills, no audit surface. Runs on Node 20+, Bun, Deno, and Cloudflare Workers.

🔄

Serverless-ready caching

Bearer tokens are cached per instance. Plug in Redis, KV, or DynamoDB via a simple cache interface to survive cold starts.

💸

Exact money strings

Amounts are decimal strings reused byte-for-byte across URLs and digests — no float formatting drift breaking hash verification.

🧭

Fully typed

Every response code (100–155) mapped to typed errors. Dual ESM/CJS output with strict TypeScript declarations.

How it works

Four steps between your server, the customer, and the M-PAiSA gateway.

Handshake

Your server exchanges credentials for a Request ID and auth digest. The SDK verifies the digest locally before anything moves — proving the gateway response hasn't been tampered with.

Redirect

The customer is sent to the gateway-hosted Payments Page, where they enter their M-PAiSA wallet credentials and complete SMS/OTP two-factor authentication.

Return

The gateway redirects the customer back with a tokenv2 hash. mpaisa-js recomputes it and compares with timing-safe equality — a mismatch throws a TokenMismatchError.

Confirm & fulfil

confirmRedirect() chains hash verification with an authoritative status API call. Only when both pass do you fulfil the order.

Security note: always verify the tokenv2 hash and confirm status server-side before fulfilling orders. Unverified redirects are vulnerable to tampering. mpaisa-js makes skipping these checks hard on purpose — you'll get a TokenMismatchError, not a silent pass.

Serverless & edge deployments

Tokens are cached per instance. For serverless, plug in an external store so tokens survive cold starts.

import { Mpaisa } from "mpaisa-js";
import Redis from "ioredis";

const redis = new Redis(process.env.REDIS_URL!);

const mpaisa = new Mpaisa({
  clientId: process.env.MPAISA_CLIENT_ID!,
  clientSecret: process.env.MPAISA_CLIENT_SECRET!,
  tokenCache: {
    get: (key) => redis.get(key),
    set: (key, value, ttlMs) =>
      redis.set(key, value, "PX", ttlMs),
  },
});

Any async key-value store works — Redis, Cloudflare KV, Durable Objects, DynamoDB, or your own.

Error handling

Every error extends MpaisaError. Secrets are auto-redacted from messages and details.

ErrorWhen it throws
ValidationErrorBad input before any network call (e.g. malformed amount)
NetworkErrorFetch failed or timed out after retries
GatewayErrorGateway returned an unusable or error response
RateLimitErrorHTTP 429 from the gateway (includes retryAfterSeconds)
TokenMismatchErrortokenv2 hash mismatch — treat as a security incident
PollTimeoutErrorTransaction still PENDING after your deadline

Handling PENDING

If the customer's browser closed mid-redirect, no callback arrives. Poll until you get a definitive answer.

const record = await mpaisa.poll(
  {
    rId: session.requestID,
    tId: "ORDER-123",
    cId: process.env.MPAISA_CLIENT_ID!,
  },
  {
    timeoutMs: 120_000,  // give up after 2 minutes
    intervalMs: 2_000,   // poll every 2s (exponential backoff, capped at 30s)
  },
);
// record.status is terminal: "success" | "cancelled" | "unknown"
// Throws PollTimeoutError if still PENDING after timeoutMs
